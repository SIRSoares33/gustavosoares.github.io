Visão do ecossistema

Menos repetição. Mais intenção no código.

O Psalms encapsula problemas recorrentes em pacotes independentes e extensíveis. Cada biblioteca pode ser adotada isoladamente, sem obrigar a aplicação a usar o restante do ecossistema.

01

Convenções claras

Padrões compreensíveis e bons valores padrão para reduzir decisões repetidas entre APIs.

02

Extensão sem mistério

Abstrações explícitas e pontos de substituição quando cache, persistência ou templates precisarem evoluir.

03

Componentes independentes

Email, autenticação e dados resolvem responsabilidades separadas e podem ser combinados apenas quando fizer sentido.

Email workflows e confirmação de comandos

Psalms.AspNetCore.EmailSender

Uma biblioteca para operações que só devem ser executadas depois que o usuário confirma a ação por um link enviado por email.

GitHub ↗ NuGet ↗ README ↗

Dor recorrente

O mesmo fluxo refeito em cada aplicação

Cadastro, reset de senha, alteração de email e aprovações exigem token, expiração, cache, template, envio, desserialização e invalidação após uso.

Decisão arquitetural

O comando vira a unidade do workflow

O IRequest original fica armazenado temporariamente e retorna ao pipeline do MediatR somente após a confirmação.

Arquitetura

  4. 04

  5. 05

  6. 06

  7. 07

  12. 12

  13. 13

Autenticação, access tokens e refresh tokens

Psalms.AspNetCore.Auth.Jwt

Uma biblioteca leve para emissão de access tokens e gestão de refresh tokens com estratégias substituíveis de persistência.

Nota: o README usa Psalms.AspNetCore.Jwt como nome de apresentação; o ID publicado no NuGet inclui Auth.

GitHub ↗NuGet ↗README ↗

Dor recorrente

JWT vai além de gerar uma string

Issuer, audience, assinatura, validade, geração segura, hash, persistência e rotação de refresh tokens precisam funcionar como um único fluxo.

Decisão arquitetural

Persistência atrás de um contrato

IPsalmsRefreshTokenRepository separa o fluxo central da tecnologia usada para guardar refresh tokens.

Componentes

Responsabilidades explícitas

PsalmsJwtTokenService

Geração de tokens, validação e rotação.

IPsalmsRefreshTokenRepository

Contrato de persistência.

DistributedCacheRepository

Implementação sobre IDistributedCache.

EFRefreshTokenRepository

Implementação com Entity Framework Core.

Fluxo 01

Autenticação

  1. 1

    Credenciais chegam à aplicação.

  2. 2

    A identidade é validada.

  3. 3

    Claims → IPsalmsJwtTokenService

  4. 4

    O access token é assinado.

  5. 5

    Um refresh token aleatório de 32 bytes é gerado.

  6. 6

    O hash é persistido.

  7. 7

    O cliente recebe o par.

Fluxo 02

Renovação e rotação

  1. 1

    O cliente envia access e refresh tokens.

  2. 2

    Token e expiração são validados.

  3. 3

    O valor é comparado com o hash.

  4. 4

    O fluxo solicita a exclusão do token anterior.

  5. 5

    Um novo access token é criado.

  6. 6

    Um novo refresh token é persistido.

  7. 7

    O novo par retorna ao cliente.

Distributed cache

Redis · SQL Server cache

Estratégia para processos distribuídos que compartilham uma implementação de IDistributedCache.

Entity Framework

Persistência consultável

Usa IPsalmsRefreshTokenEFContext para salvar e remover tokens em banco.

Repositório próprio

Outro provedor, mesmo fluxo

A aplicação implementa IPsalmsRefreshTokenRepository sem modificar o núcleo.

Mecanismos de segurança

Camadas que reduzem risco quando bem configuradas

  • Refresh token: RandomNumberGenerator
  • Hash: PasswordHasher do ASP.NET Core Identity
  • Validação configurável de issuer, audience, assinatura e lifetime
  • Rotação emite um novo par após validar o anterior
appsettings.json
{
  "JWT": {
    "Key": "configure-via-secret-manager",
    "Issuer": "your-app",
    "Audience": "your-app-users",
    "Expires": "1"
  }
}

Exemplo ilustrativo: segredos reais devem vir de secret managers, variáveis de ambiente ou mecanismo equivalente — nunca do repositório.

AuthService.cs
public class AuthService
{
    private readonly IPsalmsJwtTokenService _jwt;

    public AuthService(IPsalmsJwtTokenService jwt)
    {
        _jwt = jwt;
    }

    public async Task<AuthResponse> Authenticate(
        IEnumerable<Claim> claims)
    {
        return await _jwt.GetAuthResponseAsync(claims);
    }
}

Persistência, Repository e Unit of Work

Psalms.EFCore.DataManagement

A implementação Entity Framework Core do projeto Psalms.DataManagement, criada para aplicações que optam pelos padrões Repository e Unit of Work.

GitHub ↗NuGet ↗README ↗

Dor recorrente

Acesso a dados inconsistente entre projetos

CRUD, predicados, coleções relacionadas, SaveChanges e registro no container costumam reaparecer com contratos diferentes.

Decisão arquitetural

Uma API comum sobre o DbContext

O repositório concentra operações recorrentes; a Unit of Work coordena o contexto e confirma as mudanças.

Arquitetura

Uma cadeia curta e explícita

Application Service↓IPsalmsUnitOfWork<TContext>↓IPsalmsEfCoreRepository↓Entity Framework DbContext↓Database
IPsalmsUnitOfWork<TContext>

Expõe Repository, executa SaveChangesAsync e coordena o descarte do contexto.

IPsalmsEfCoreRepository

Centraliza consultas e alterações genéricas para diferentes entidades.

DbContext

Mantém tracking e conversa com o provider configurado.

API confirmada

Operações públicas do pacote

CreateAsync<T>(T entity)DeleteAsync<T>(int id)GetByIdAsync<T>(int id)GetByAsync<T>(predicate)ExistsAsync<T>(predicate)GetAllAsync<T>()GetCollectionFromEntityAsync<...>(...)RepositorySaveChangesAsync()DisposeAsync()

A classe concreta PsalmsEfCoreRepository também contém UpdateAsync<T>, mas a versão 1.0.0 não expõe esse método em IPsalmsEfCoreRepository; por isso ele não aparece como parte do contrato principal acima.

Program.cs
services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(
        Configuration.GetConnectionString("Default")));

services.AddScoped<
    IPsalmsUnitOfWork<AppDbContext>,
    PsalmsUnitOfWork<AppDbContext>>();
ProductService.cs
public class ProductService
{
    private readonly IPsalmsUnitOfWork<AppDbContext> _uow;

    public ProductService(
        IPsalmsUnitOfWork<AppDbContext> uow)
    {
        _uow = uow;
    }

    public async Task AddProductAsync(Product product)
    {
        await _uow.Repository.CreateAsync(product);
        await _uow.SaveChangesAsync();
    }

    public async Task<Product?> GetProductAsync(int id)
    {
        return await _uow.Repository
            .GetByIdAsync<Product>(id);
    }
}

services.AddDbContext<AppDbContext>(options =>

Arquitetura integrada

Como os pacotes podem trabalhar juntos

Um cenário possível para uma API ASP.NET Core. A integração é opcional: cada pacote continua independente e pode ser adotado sozinho.

Client↓ASP.NET Core API↓Psalms.AspNetCore.Auth.Jwt↓Psalms.AspNetCore.EmailSender↓MediatR Command Handler↓Psalms.EFCore.DataManagement↓Entity Framework Core↓Database
  1. JWT

    Autentica o usuário e gerencia access e refresh tokens.

  2. EmailSender

    Armazena o comando sensível e envia a confirmação.

  3. MediatR

    Encaminha o comando restaurado ao handler.

  4. DataManagement

    Repository e Unit of Work persistem a alteração.
