Visão geral

O projeto

O domínio é simples de propósito: assim, o estudo pode se concentrar nas decisões que sustentam uma API organizada.

Mais do que um CRUD

ToDo API é uma API REST para gerenciamento de usuários e tarefas. A solução usa ASP.NET Core, autenticação JWT, autorização por roles, MediatR e Entity Framework Core em camadas inspiradas na Clean Architecture.

Finalidade educacional

O objetivo é transformar conceitos estudados separadamente em uma aplicação coerente, exercitando dependências, contratos, regras, persistência e execução de forma semelhante às preocupações de um projeto real.

Estado auditado do código

Autenticação e usuários estão ativos; tarefas aguardam integração à API compilada.

Os commands, queries, handlers, serviços, repositório e regras de propriedade das tarefas existem. Entretanto, TasksController.cs está em ToDo.Api/, enquanto o projeto compilado fica em Todo.Api/. Em sistemas com diferenciação entre maiúsculas e minúsculas, esse controller não entra no assembly atual. Por isso, as rotas de tarefas são apresentadas nesta página como implementação pendente de integração, e não como endpoints disponíveis.

Motivação

Por que construí este projeto?

Desenvolvi o ToDo API para transformar conceitos estudados separadamente em uma aplicação backend completa e organizada. A ideia não era apenas criar endpoints de tarefas, mas entender como autenticação, autorização, regras de negócio, persistência, casos de uso, configuração e infraestrutura se conectam em um projeto ASP.NET Core.

Escolhi um domínio conhecido para direcionar a atenção ao que realmente queria exercitar: separação de responsabilidades, proteção de endpoints, identificação do usuário autenticado, comunicação entre camadas, testabilidade e execução reproduzível.

O projeto também funciona como espaço de revisão. As limitações encontradas fazem parte do aprendizado e ajudam a transformar decisões implícitas em próximos passos concretos.

  • Organização das dependências
  • Autenticação e autorização

Do HTTP ao banco

Como uma requisição percorre a aplicação

Cliente→AuthController→LoginCommand→MediatR→LoginHandler→IAuthService→UserRepository→PostgreSQL
  1. A API recebe e interpreta a requisição HTTP.
  2. O controller cria um command ou query com o contrato necessário.
  3. O MediatR encontra o handler correspondente.
  4. O handler delega a regra ao serviço de aplicação.
  5. A implementação de Infrastructure consulta ou persiste dados.
  6. O resultado retorna ao controller, que define a resposta HTTP.

Por que MediatR?

Ele funciona como intermediário entre HTTP e casos de uso. Isso mantém controllers menores, explicita cada intenção e facilita testar handlers isoladamente. O projeto não implementa pipeline behaviors neste momento.

Identidade e acesso

Autenticação e autorização

Autenticação confirma quem faz a requisição; autorização verifica se essa identidade pode executar a operação.

1

Cadastro ou login

Credenciais entram por AuthController e são validadas.

2

Token

O serviço gera um JWT após verificar a senha armazenada com hash.

3

Claims

O token contém NameIdentifier, Email, Name e Role.

4

Autorização

O middleware valida o token e os atributos [Authorize] aplicam as restrições.

Header de uma rota protegida

Authorization: Bearer {token}

Roles confirmadas

AdminUser

NameIdentifier conecta a identidade às operações do próprio usuário. Role diferencia ações administrativas das ações autenticadas comuns. Não há refresh token no estado atual.

Dados e contratos

Persistência, DTOs e validações

PERSISTÊNCIA

EF Core + PostgreSQL

AppDbContext expõe Users e Todos. Npgsql conecta a aplicação ao PostgreSQL, migrations versionam o esquema e repositórios assíncronos isolam as consultas.

CONTRATOS

DTOs + AutoMapper

DTOs controlam entradas e saídas sem expor diretamente as entidades. Isso reduz overposting e permite que contratos HTTP e domínio evoluam com responsabilidades distintas.

VALIDAÇÃO

FluentValidation + Value Objects

Validators verificam os DTOs; Value Objects reforçam regras no domínio. Título é obrigatório e limitado a 100 caracteres, descrição a 500, email precisa ser válido e senha exige ao menos oito caracteres e diversidade de tipos.

ERROS

Middleware centralizado

ExceptionMiddleware converte exceções conhecidas em 400, 401, 404 ou 422 e mantém 500 como fallback. A resposta atual usa { status, error }; ainda não há ProblemDetails.

Propriedade das tarefas

TodoService obtém o ID pelo NameIdentifier. Criação, consulta, atualização e exclusão filtram por UserId, impedindo que uma conta manipule tarefas de outra no nível de serviço e repositório. Essa proteção ficará acessível por HTTP após a integração do controller.

Na configuração local do ASP.NET Core, o duplo underscore de JWT__Key representa a hierarquia JWT:Key.

Execução com Docker

O Compose publica a API em http://localhost:8080 e o PostgreSQL em 5432. A rede padrão do Compose conecta os serviços e o volume pgdata persiste o banco.

Explorando a API
http://localhost:8080/swagger

O Swagger atual permite visualizar e executar os contratos ativos. Entretanto, AddSwaggerGen() ainda não registra um esquema de segurança Bearer; por isso, o fluxo de autenticação via botão Authorize precisa ser configurado antes de testar rotas protegidas diretamente pela interface.

Limitações confirmadas do Compose

depends_on define ordem de inicialização, mas não aguarda o banco ficar pronto porque não há health check. O serviço PostgreSQL também recebe apenas POSTGRES_PASSWORD; portanto, usar outro DB_NAME exige criar o banco ou adicionar POSTGRES_DB ao Compose.

Biblioteca reutilizada

Psalms aplicado em um projeto prático

Psalms.AspNetCore.Auth.Jwt 4.0.0

Autenticação JWT sem repetir toda a infraestrutura

O pacote é referenciado por ToDo.Infrastructure, registrado por AddPsalmsJwtAuthentication(configuration) e utilizado por PsalmsJwtTokenService para emitir tokens.

O ToDo API serviu como cenário de aplicação para validar a biblioteca em conjunto com claims, roles e Dependency Injection. O projeto continua responsável pela verificação de credenciais e pelas regras de acesso.

Reflexão

Principais aprendizados

Aprendi que uma API organizada exige mais do que endpoints funcionando. Autenticação e autorização resolvem problemas diferentes, e as claims são o elo entre a identidade do usuário e as regras da aplicação.

Separar camadas tornou as dependências mais visíveis. MediatR ajudou a isolar casos de uso, enquanto os DTOs protegeram os contratos externos. Ao mesmo tempo, o projeto mostrou que abstrações só agregam valor quando continuam proporcionais ao problema.

Docker reduziu diferenças entre ambientes, mas também evidenciou que subir containers não basta: prontidão do banco, variáveis consistentes, segredos e observabilidade precisam ser tratados explicitamente.

O aprendizado mais importante foi revisar o próprio código com honestidade. Encontrar uma rota implementada fora do projeto compilado reforçou a importância de validar a aplicação como ela realmente é executada.
